### 9 Bots messaging each other, groups under a lead, loop prevention

## Where Bate is ahead or right to differ

- **No relay.** Issue #26 title "…with no relay"; `PROTOCOL.md:463` "nothing in between relays messages". nightly routes Slack, Discord and Telegram events through its own service (`docs/messaging.md:11-14`), which needs an account and a hosted route. Fine for one Mac.
- **Pairing direction.** The owner mints the code in the window, so a stranger cannot make Bate store anything or queue a request. OpenClaw and nanobot have strangers get codes and keep a pending list (`pairing.md:35`; `configuration.md:2393`). Bate's code is 5 min and 5 tries (`channels.rs:49-50`).
- **Token handling.** Channel tokens are not sent to a window or an engine and are scrubbed from errors (`channels.rs:175-195`, `PROTOCOL.md:474`). Others keep tokens in config files (OpenClaw `telegram.md:98-108`, nanobot `chat-apps.md:158`).
- **Outside data in a prompt.** A webhook body and a `/run` tail are fenced by a random line per request and the model is told to treat them as data (`core.rs:3115-3122`). Hermes also warns that payloads are untrusted (`webhooks.md:85`), but does not fence with a per-request line in the docs read.
- **Loop prevention by construction.** A bot waiting for a reply is busy and refuses a message sent back (`core.rs:2053-2055`), so no hop counter or window is needed; Hermes and OpenClaw need counters (`bot_loop_guard.py:1-12`, `bot-loop-protection.md:23-25`). Lead "cannot stop or redirect" is a stated choice (issue #33).
- **Schedule math.** Clock-change cases are tested and a slot is sent once across a crash (`schedule.rs:322-360`, `core.rs:3213-3234`). OpenClaw and nanobot document that missed runs are dropped; Bate runs one if at most 6 h old and records `missed` otherwise.
- **Webhook from a web page.** `Origin` is refused (`hooks.rs:198-200`). Level with nightly (`docs/architecture/agents.md:244`); OpenClaw uses a header token instead.
