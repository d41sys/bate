# Technology inside Kwant, Brigade and AionUi

Read from the shallow clones named in the [README](README.md). Each cell cites `path:line` in that app's repo. A path given without its folders repeats a path cited in full earlier in the same row. Row 1 (languages) is in the README, where every app is counted the same way.

The three apps run agent engines in different ways, and AionUi has no agent loop in the cloned repo.

| App | Engines and protocol |
|---|---|
| Kwant | Own Rust API loop, plus per-turn child processes for `claude -p`, `codex exec` and `grok`. Output is parsed from stdout; the CLIs call back into Kwant over MCP. |
| Brigade | pi's in-process loop for API models. `claude` runs as a "harness" child process under pi, parsed from stream-json, with tools served back over loopback MCP. No Codex CLI, Gemini CLI or ACP. |
| AionUi | No loop in this repo. A separate Rust binary (`aioncore`, from the AionCore repo) runs the agents and speaks ACP to CLIs. The cloned repo only launches it and talks to it over HTTP and WebSocket. |

## Notes

- **AionUi's agent engine is not in the cloned repo.** The `aioncore` binary, which holds the agent loop, ACP client, storage, scheduling, channels and MCP management, is built from the separate AionCore repo and bundled at install time (`docs/architecture/overview.md:15-18`, `readme.md:713`). The Row 8, 9, 12 and 13 cells for AionUi therefore describe only the types, the launcher and the extension surface visible here. Reading AionCore is needed to say which agents speak native ACP and which run through adapters.
- **AionUi's root `package.json` lists many unused dependencies.** `@agentclientprotocol/sdk`, `express`, `grammy`, `croner`, `better-sqlite3`, the Lark, DingTalk and WeCom SDKs and others appear in `package.json`. A grep of `packages/` and `scripts/` found imports only for `better-sqlite3`, `ws`, `electron-updater`, `electron-log`, `fix-path`, `@sentry/electron`, `@modelcontextprotocol/sdk` and the three model SDKs. `packages/desktop/src/process/services/database` is used for legacy migration. Treat the rest as leftover or backend-side. The `Dockerfile` also references scripts I did not find.
- **Kwant's server runs inside the Tauri app, and "VM" means Docker.** The Mac shell calls `kwnt::serve::run` on a thread in the app process (`apps/mac/src/main.rs:566-571`), while `src/app_update.rs:1` says "its own process". "Agents in VM" and "VM" computer mode are Docker containers, not hypervisor VMs (`src/sandbox/agent_vm/mod.rs:8`, `computer.rs:1-4`). Seatbelt is opt-in (`mac_local.rs:31`).
- **Brigade's `codex` entries are not the Codex CLI.** They are pi OAuth providers that reuse `~/.codex/auth.json` (`src/integrations/cli-login.ts:56-89`). Claude Code is the only external agent binary that Brigade runs. Brigade lists no MCP client in the code, though README line 130 says it can "connect MCP servers in". Its `AGENTS.md:105` says "libsodium seal" while `SECURITY.md:97` says AES-256-GCM, and I found neither in the dependencies.
- **Test counts are approximate.** They come from directory listings (for example Kwant `tests/` has about 239 files and `frontend/tests/` about 256). Brigade's 281 test files come from `AGENTS.md`, not a count.
- **Kwant has no keychain, no cron crate and no vendor SDK.** Secrets are encrypted files and SQLite. Routine scheduling is hand-written. Model calls use raw `reqwest`. CI never builds `apps/mac` on every push: `mac.yml` runs on PRs that touch `apps/mac`, and `ci.yml` only checks that its lockfile is in sync.
